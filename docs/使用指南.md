# CogNet 使用指南

CogNet 是一个 **Kubernetes 原生的 AI Agent 控制平面**。它用 Operator 模式,以声明式
CRD 的方式管理 Agent 以及它所依赖的一切资源(Model / Tool / Skill / MCPServer /
Workflow / Prompt / Memory / Policy …),并通过 **Registry** 把解析后的配置下发给运行时。

> **重要定位**:CogNet **不是 Agent 运行时**。它不做推理、不做 planner/ReAct、不做
> tool-calling、不实现 memory。它只负责**声明、生命周期管理、配置聚合、服务发现、状态同步、
> 可观测**。真正执行的是"运行时"(LangGraph / OpenAI Agents SDK / CrewAI / 你自研的),
> 运行时只跟 Registry 打交道,不直接访问 Kubernetes API。

## 1. 架构

```
        控制平面 (Control Plane)                     数据面 (Data Plane)
  ┌──────────────────────────────────┐        ┌──────────────────────────┐
  │  kube-apiserver (CRDs)            │        │  Agent Runtime           │
  │        ▲ watch/reconcile          │        │  MCP Runtime / Tool      │
  │  ┌─────┴─────┐   ┌────────────┐   │        │        ▲ HTTP/SSE(配置)  │
  │  │ Operator  │──▶│  Registry  │◀──┼────────┼────────┘                 │
  │  │(cmd/main) │   │(cmd/registry)  │        │  运行时从不直接访问        │
  │  └───────────┘   └────────────┘   │        │  kube-apiserver          │
  └──────────────────────────────────┘        └──────────────────────────┘
```

- **Operator**(`cmd/main.go` + `internal/controller/`):监听所有 CogNet 资源,校验、解析
  引用、物化工作负载(如 MCPServer→Deployment/Service)、发布 status。
- **Registry**(`cmd/registry/`):运行时唯一的配置来源。
  - `GET /v1/agents/{ns}/{name}/config` —— 一次性拉取解析后的完整配置。
  - `GET /v1/agents/{ns}/{name}/watch` —— SSE 流,Agent 一变化就推送新配置(**热更新**)。
- **准入 Webhook**(`internal/webhook/`):在 apply 时做结构性校验(快速失败)。

**核心闭环**:声明资源 → Operator 解析引用并算出 `resolvedConfigHash` → 写入 Agent status
→ Registry 监听 Agent 变化并经 SSE 推给运行时 → 运行时对比 hash 不同则热重载。

## 2. 资源模型(14 个 CRD)

API 组:`core.cognet.io/v1alpha1`,全部为 Namespaced。

| Kind | 短名 | 作用 |
|---|---|---|
| **Agent** | ag | 用"对能力资源的引用集合"声明一个 Agent(核心) |
| **AgentClass** | agc | Agent 的可复用默认值 |
| **Model** | — | 模型端点(openai/anthropic/azure/ollama/vllm/openrouter/custom) |
| **Tool** | — | 一个可被**调用**的能力(http/grpc/mcp/wasm/plugin/container) |
| **ToolSet** | ss | 一组 Tool 的命名捆绑 |
| **Skill** | — | markdown 指令包(SKILL.md 式),教 agent **怎么做**;可声明 `allowedTools` |
| **MCPServer** | mcp | MCP 服务;Operator 自动物化成 Deployment+Service |
| **Workflow** | wf | 引擎无关的执行流程(planner/tool/reflect/finish) |
| **PromptTemplate** | pt | 版本化的 system/role prompt + few-shot |
| **Memory** | — | 记忆/存储后端(redis/postgres/vector/graph/s3) |
| **KnowledgeBase** | kb | 检索语料库(RAG) |
| **Policy** | — | 对 models/memory/mcp/tools/workflows 的粗粒度 allow/deny |
| **ToolPolicy** | tp | 单 Tool 级别的细粒度授权与限频 |
| **Credential** | cred | 通过 K8s Secret 间接引用密钥(绝不内联密钥) |

查看:`kubectl get crd | grep cognet`、`kubectl explain agent.spec`。

## 3. 前置条件与部署

**工具**:Go 1.24+、Docker、kubectl、一个 K8s 集群(本地推荐 OrbStack / kind / minikube)。

### 3.1 本地集群部署(无 cert-manager,关闭 webhook)

```sh
# 假设 kubeconfig 的 current-context 已指向本地集群
export KUBECONFIG=$HOME/.kube/config

# 1. 构建 operator 镜像(本地 Docker 与集群共享镜像时无需 push)
make docker-build IMG=cognet:dev

# 2. 部署:仅 CRD + RBAC + manager(config/local overlay,已设 ENABLE_WEBHOOKS=false)
bin/kustomize build config/local | kubectl apply -f -

# 3. 若镜像 tag 不变但内容更新,强制滚动
kubectl -n agent-plane-system rollout restart deploy/agent-plane-controller-manager
kubectl -n agent-plane-system rollout status  deploy/agent-plane-controller-manager
```

> `config/local` 是本地专用 overlay(不含 webhook/cert-manager)。完整版在 `config/default`
> (需要 cert-manager,`make deploy IMG=…`)。

### 3.2 生产/集群内启用 Webhook

需先装 cert-manager,再用 `config/default`(取消 `config/default/kustomization.yaml` 里
webhook / cert-manager 段的注释),并去掉 manager 的 `ENABLE_WEBHOOKS=false`。

## 4. 声明式用法:YAML 定义一个 Agent

一个 Agent = 若干引用。下面是最小可用示例(先建 Model,再建 Agent):

```yaml
apiVersion: core.cognet.io/v1alpha1
kind: Model
metadata: {name: my-model}
spec:
  provider: openrouter
  modelName: openai/gpt-4o-mini
  credentialRef: {name: my-key}      # 可选
---
apiVersion: core.cognet.io/v1alpha1
kind: Credential
metadata: {name: my-key}
spec:
  secretRef: {name: my-secret, key: api-key}   # 指向一个普通 K8s Secret
---
apiVersion: core.cognet.io/v1alpha1
kind: Agent
metadata: {name: my-agent}
spec:
  modelRef: {name: my-model}
  # 可选:promptRef / toolRefs / toolSetRefs / skillRefs / memoryRefs / policyRefs / agentClassRef
```

```sh
kubectl apply -f my-agent.yaml
kubectl get agent my-agent           # 看 PHASE(Pending/Ready/Degraded)
kubectl describe agent my-agent      # 看 conditions(Resolved / Ready)与 resolvedConfigHash
```

**引用缺失会怎样?** Agent 变 `Degraded`,reason=`ReferenceNotFound`。等你把缺的资源建出来,
Agent 会**自动收敛**为 `Ready`(控制器 watch 了被引用的资源)。这是 GitOps 友好的关键:
apply 顺序无所谓。

`config/samples/` 有一套相互关联的完整样例:`kubectl apply -k config/samples`。

## 5. 代码用法:用 Go 编程创建 Agent

如果不想写 YAML,可以直接用 typed client 创建(把 CogNet 的 API 当库用)。参考
`cmd/demo/main.go`,核心就是把 CR 当普通 Go struct 创建:

```go
import (
    corev1 "k8s.io/api/core/v1"
    metav1 "k8s.io/apimachinery/pkg/apis/meta/v1"
    "sigs.k8s.io/controller-runtime/pkg/client"
    "github.com/hkmdxlftjf/agent-plane/api/v1alpha1"
)

// k 是一个 controller-runtime client(scheme 里注册了 v1alpha1)
_ = k.Create(ctx, &v1alpha1.Model{
    ObjectMeta: metav1.ObjectMeta{Name: "llm-model", Namespace: ns},
    Spec: v1alpha1.ModelSpec{
        Provider: "custom", ModelName: "claude-haiku-4-5-20251001",
        Endpoint: "http://gateway/v1",
        CredentialRef: &v1alpha1.LocalReference{Name: "llm-cred"},
    },
})
_ = k.Create(ctx, &v1alpha1.Agent{
    ObjectMeta: metav1.ObjectMeta{Name: "support-agent", Namespace: ns},
    Spec: v1alpha1.AgentSpec{
        ModelRef:  v1alpha1.LocalReference{Name: "llm-model"},
        PromptRef: &v1alpha1.LocalReference{Name: "support-prompt"},
        ToolRefs:  []v1alpha1.LocalReference{{Name: "order-lookup"}},
    },
})
// 然后轮询 agent.Status.Phase == v1alpha1.AgentPhaseReady
```

直接运行完整的代码版 demo(创建 → 等待 → 进程内 port-forward → 跑 agent → 清理):

```sh
export KUBECONFIG=$HOME/.kube/config
go run ./cmd/demo "K-7 这个订单什么状态?告诉我承运商和预计送达时间"
```

## 6. 数据面:Registry 下发与热更新

运行时不读 K8s,只读 Registry。

```sh
make run-registry &          # 或 go run ./cmd/registry(默认 :9090)

# 拉取解析后的配置(含 model 端点、Secret 坐标、已解析的 tools 定义)
curl -s localhost:9090/v1/agents/default/my-agent/config | jq

# 订阅热更新:另开一个终端改 Agent/依赖,这里会立刻收到新配置
curl -N localhost:9090/v1/agents/default/my-agent/watch
```

**热更新链路**(以改 Tool 为例):改 Tool → Agent 控制器(watch 了 Tool)重算
`resolvedConfigHash` → Registry(watch 了 Agent)经 SSE 推新配置 → 运行时热重载。
注意 Registry **只下发 Secret 的坐标(name/key),不下发密钥值**;密钥由运行时用自己的 RBAC
去读 Secret。

## 7. 跑一个真实 Agent(工具/MCP 调用)

`cmd/agent-runtime` 是一个**最小但真实**的运行时(代表 LangGraph 那类框架),它:
1. 从 Registry 拉配置;2. 用自己的 RBAC 读 Secret 拿 API key;3. 从 PromptTemplate 取 system
prompt;4. 跑 **tool-calling 循环**——模型要求调工具,运行时真的去调(`http` 走 POST,`mcp`
走 JSON-RPC `tools/call`),把结果回喂模型,直到出最终答案。

```sh
make run-registry &
# 若工具是集群内 MCP,宿主机需 port-forward,再用 --tool-endpoint 覆盖端点
kubectl -n default port-forward svc/orders-mcp 18080:8080 &
go run ./cmd/agent-runtime \
  --namespace default --name my-agent \
  --tool-endpoint order-lookup=http://localhost:18080 \
  --prompt "订单 A-42 的状态?"
```

工具调用循环的可复用实现在 `internal/agentloop/`,`agent-runtime` 与 `demo` 共用。

## 10. Tool 与 Skill 的区别

这是最容易混淆的一点:

| | **Tool**(可执行能力) | **Skill**(markdown 指令包) |
|---|---|---|
| 本质 | 一个可被**调用**的端点 | 一份教模型**怎么做**的说明文档 |
| 类比 | API / 函数 | 操作手册 / SKILL.md |
| 内容 | endpoint + schema + 超时 | 正文(内联或 ConfigMap)+ allowedTools |
| 谁消费 | 运行时发起调用 | 模型读它、决定何时用 |
| 类型 | http/grpc/mcp/wasm/plugin/container | — |

Agent 里 `toolRefs` 引用 Tool,`skillRefs` 引用 Skill,两者可同时用。

## 11. 常见问题(FAQ)

**Q: kubectl 连错集群了?**
很多环境的 shell profile 会 `export KUBECONFIG=/path/to/some.config`,导致 kubectl 指向
别的集群。操作本地集群时显式指定:`export KUBECONFIG=$HOME/.kube/config`(确认
`kubectl config current-context` 是你的本地集群)。

**Q: manager Pod 一直 CrashLoop?**
多半是启用了 webhook 但没有证书。本地部署用 `config/local`(已设 `ENABLE_WEBHOOKS=false`),
或安装 cert-manager。

**Q: MCPServer 的 Pod 一直 ImagePullBackOff?**
镜像不存在。样例里的 `ghcr.io/cognet/example-...` 是占位符;真实使用请替换为可拉取的镜像,
或用本地共享镜像(OrbStack/kind:`docker build` 后 tag 用非 `:latest`,拉取策略默认
`IfNotPresent`)。

**Q: 宿主机上的运行时连不上集群内 MCP 的 `*.svc` 地址?**
这是 host↔cluster 网络问题,不是设计缺陷。集群内的真实运行时可直接用 svc DNS;宿主机演示时
`kubectl port-forward` 后用 `--tool-endpoint name=url` 覆盖(`cmd/demo` 用 client-go
在进程内做了 port-forward,无需外部 kubectl)。

**Q: 改了 CRD 字段后 apply 报 unknown field?**
集群里的 CRD 是旧 schema。重新 `make manifests` 后 `kubectl apply -k config/crd`(或
`config/local`)更新 CRD。

**Q: 密钥会不会被 Registry 泄露?**
不会。Registry 只下发 Secret 的 name/key 坐标,密钥值由运行时用自己的 RBAC 读取。

## 12. 目录结构

```
api/v1alpha1/           # 14 个 CRD 的类型定义 + 共享类型 + 结构校验(validation.go)
internal/controller/    # 每个 Kind 一个 reconciler;refutil.go 是共享的引用解析/watch 工具
internal/webhook/       # 校验型准入 webhook(Agent/Workflow/Tool)
internal/agentloop/     # 可复用的 tool-calling 循环(验证用,非控制平面)
cmd/main.go             # Operator(manager)入口
cmd/registry/           # Registry(数据面配置端点:/config、/watch)
cmd/agent-runtime/      # 真实运行时验证工具(从 Registry 驱动)
cmd/demo/               # 纯代码版一键 demo(typed client 创建 + 进程内 port-forward)
cmd/example-mcp/        # 验证用的最小 MCP server(测试夹具)
config/crd|rbac|manager # kustomize 基础
config/default          # 完整部署(含 webhook/cert-manager)
config/local            # 本地部署 overlay(无 webhook)
config/samples          # 一套相互关联的样例资源
config/demo             # 一个完整 Agent demo 的清单
hack/demo.sh            # 一键 demo 脚本
hack/functional-test.sh # 活集群功能测试(19 项)
```

> `cmd/agent-runtime`、`cmd/demo`、`cmd/example-mcp` 是**验证用的测试夹具**,不属于控制平面
> 本身——它们代表"接入方"(真实 Agent 框架、真实 MCP 工具服务),用来证明平台能端到端驱动它们。
